# UA Scholar

Scholarship and grant portal for the University of the Assumption.
Built with **Next.js 15 (App Router)** for frontend + backend, **Supabase** (Auth, Postgres, Storage),
and **Prisma** for the database schema and migrations.

## Setup

### 1. Install
```bash
npm install
cp .env.local.example .env.local
```
Then set `AES_SECRET_KEY` in `.env.local` to a random string of at least 32 characters
(for example, one generated by a password manager).

### 2. Supabase
1. Create a project at https://supabase.com and copy the **Project URL** and **anon key** into `.env.local`.
2. Copy the **Session pooler** connection string (Dashboard > Connect, port 5432) into `DATABASE_URL`.
3. Create the database and load the scholarships:
   ```bash
   npm run db:migrate   # applies prisma/migrations (tables + security)
   npm run db:seed      # inserts the 8 UA scholarships
   ```
4. **Authentication > URL Configuration**: set *Site URL* to `http://localhost:3000` and add
   `http://localhost:3000/auth/callback` to *Redirect URLs* (add your production URL too).

### 3. Google sign-in
1. In Google Cloud Console, create an **OAuth Client ID** (Web application).
2. Add the authorized redirect URI shown in **Supabase > Authentication > Providers > Google**
   (it looks like `https://<project>.supabase.co/auth/v1/callback`).
3. Paste the Google Client ID and Secret into the Supabase Google provider and enable it.

### 4. Run
```bash
npm run dev
```

### 5. Create the first super admin
There is no public registration page. Sign in once with your UA Google account (`@ua.edu.ph`),
then run this in the Supabase SQL Editor (Dashboard > SQL Editor):
```sql
update public.profiles set role = 'super_admin' where email = 'you@ua.edu.ph';
```
Only `@ua.edu.ph` emails can create accounts (enforced by the `*_ua_students_only` migration).
Also turn off **Authentication > Providers > Email > Allow new users to sign up** in Supabase.
From then on, the super admin promotes other users and assigns scholarships under **Admin > Account Management**.

## Database (Prisma)

| File | What it contains |
|---|---|
| `prisma/schema.prisma` | Tables, enums, relations, indexes (the source of truth for the schema) |
| `prisma/migrations/*_init` | SQL generated from `schema.prisma` |
| `prisma/migrations/*_security` | Hand-written SQL: RLS policies, helper functions, triggers, grants, CHECK constraints, Storage bucket |
| `prisma/seed.sql` | Initial scholarships |
| `prisma.config.mjs` | Prisma 7 config (reads `DATABASE_URL` from `.env.local`) |

**Prisma is used for the schema only.** At runtime the app talks to the database through Supabase
as the logged-in user, so Row Level Security is always enforced. Prisma Client would connect as the
database owner and **bypass RLS**, so do not use it to read or write user data.

### Changing the schema
1. Edit `prisma/schema.prisma` (`npm run db:validate` to check it).
2. `npm run db:new -- describe_change` creates `prisma/migrations/<timestamp>_describe_change/migration.sql`.
3. Read the SQL, then run `npm run db:migrate`.
4. If you add a table, also add its RLS policies and grants in a new hand-written migration
   (copy the pattern from the `*_security` migration). Tables without policies are inaccessible.

`prisma migrate dev` is not used because its temporary "shadow" database lacks Supabase's `auth`
and `storage` schemas.

## Roles

| Role | Can do |
|---|---|
| `student` | Profile, eligibility check, apply, upload documents, track status, notifications |
| `admin` (Scholarship Admin) | Review, approve or reject applications, see students, and edit **only the scholarships assigned to them** |
| `super_admin` | Everything, plus add/remove scholarships, manage accounts, roles and assignments |

## AES encryption (`app/_lib/aes-encryption.js`)

One server-only file, importable from any page, Server Action or Route Handler.
(`_lib` is a Next.js private folder, so it never becomes a route.)

```js
import { encryptStudentData, decryptStudentData, encryptAdminData } from '@/app/_lib/aes-encryption';

const cipher = encryptStudentData({ phone: '0917...' }, studentId);
const plain  = decryptStudentData(cipher, studentId, {}); // {} = fallback if empty or unreadable
```

| Function | Key | Used for |
|---|---|---|
| `encryptStudentData` / `decryptStudentData` | student | Personal info, academic records, application answers, document file names |
| `encryptStudentFile` / `decryptStudentFile` | student | Uploaded document bytes in Storage |
| `encryptAdminData` / `decryptAdminData` | admin | Admin account details, review notes (scholarship records) |

### Where it is applied

| Spec | Encrypted when... | Code |
|---|---|---|
| D1 personal info + academic records | student saves profile | `app/student/profile/actions.js` |
| D1 application + documents | student applies or uploads a file | `app/student/scholarships/[id]/apply/actions.js`, `app/student/applications/[id]/actions.js`, `lib/documents.js` |
| D2 admin account details | admin saves "My Account" | `app/admin/profile/actions.js` |
| D2 scholarship records | admin approves or rejects with notes | `app/admin/applications/[id]/actions.js` |
| D2 assigned scholarship only | checked **before decrypting** (and by RLS in the DB) | `canAccessScholarship()` in `lib/auth.js`, used by the admin review page and action, the student directory, and `/api/documents/[id]` |

- **One secret, two keys:** `AES_SECRET_KEY` → scrypt → separate student and admin AES-256 keys.
- **AES-256-GCM** detects tampering. The owner/record id is bound as AAD, so ciphertext copied into another row won't decrypt.
- **Server-only** (`import 'server-only'`): the secret and keys never reach the browser.
- **Back up `AES_SECRET_KEY`.** If it is lost or changed, encrypted data cannot be recovered.

Names, emails, statuses and scholarship listings stay plain so they can be listed, searched and filtered.

## Security summary
- Row Level Security on every table. The database itself enforces "admins only see their assigned scholarships".
- Column-level grants: students can't change their role, and admins can't edit a student's answers.
- A trigger blocks role, status and email changes unless the user is a super admin.
- Every page **and** Server Action checks the role on the server (`lib/auth.js`).
- Uploads are checked for size (5 MB), MIME type **and** file signature, encrypted, stored in a private bucket,
  and downloaded only through `/api/documents/[id]` after an access check.
- Open-redirect protection on login and OAuth `next` parameters, sanitized search input, and security headers in `next.config.mjs`.
- No Supabase service-role key is used anywhere.

## Project structure
```
app/                 pages (each with its own page.module.css) and Server Actions (actions.js)
  admin/             admin area
  student/           student area
  scholarships/      public list and details
  api/documents/     secure file download
components/<Name>/   one folder per component: <Name>.js + <Name>.module.css
lib/                 auth, supabase clients, encryption, validation, helpers
prisma/              schema.prisma, migrations (tables + security), seed.sql
```

> The benefits and eligibility text in `prisma/seed.sql` are **placeholders**. Replace them with the official
> details from the Scholarship Office through Admin > Scholarships.
